# Feature 1 — Daily Collective Sitting

**Product:** Vipassana Timer  
**Feature:** Daily Collective Sitting  
**Version:** V1  
**Status:** Product / Engineering Specification

---

## 1. Objective

Create a system that helps meditators maintain daily discipline and continuity by making them sit at a predetermined time together with other meditators.

The core experience is:

> **Commit → Arrive → See others → Start together → Meditate → Complete → Return tomorrow**

The feature is not intended to maximize engagement, screen time, social interaction, or gamification.

Its purpose is to make keeping a meditation commitment easier.

---

## 2. Product Philosophy

### Core principle

> **The social element should be felt, not consumed.**

The user should feel:

> “I am sitting with other meditators right now.”

without being distracted by:

- chat
- social feeds
- profiles
- photographs
- likes
- reactions
- leaderboards
- achievements
- unnecessary animations

Technology should facilitate the practice and then disappear.

---

# 3. Scope

## Included in V1

- Recurring daily meditation schedule
- Morning and evening time slots
- Exact start time within a slot
- Meditation duration
- Daily collective sitting
- Virtual Meditation Hall
- Anonymous meditation avatars
- Live participant count
- Pre-sit presence/check-in
- Scheduled start
- Integration with existing Vipassana Timer
- End-of-sit confirmation
- Attendance record
- Personal continuity statistics
- Minimal reminders
- Offline-resilient meditation timer

## Explicitly excluded from V1

- Buddy system
- Chat
- Direct messaging
- Social feed
- Profile photographs
- Daily meditation snaps
- Likes/reactions
- Leaderboards
- Points
- Badges
- Public rankings
- Teacher functionality
- AI companion
- Public meditation history

The buddy system will be designed as a subsequent feature using the attendance/discipline data generated by this feature.

# 4. Daily Schedule

## Morning slots

- 4:00–5:00 AM
- 5:00–6:00 AM
- 6:00–7:00 AM
- 7:00–8:00 AM
- 8:00–9:00 AM
- 9:00–10:00 AM

## Evening slots

- 5:00–6:00 PM
- 6:00–7:00 PM
- 7:00–8:00 PM
- 8:00–9:00 PM
- 9:00–10:00 PM

These are discovery/selection windows.

The user chooses an exact start time within the selected window.

Example:

> Morning → 6:00–7:00 AM → 6:30 AM

---

# 5. Meditation Duration

V1 should support:

- 30 minutes
- 45 minutes
- 60 minutes

If the existing Vipassana Timer already supports 90 minutes, Collective Sitting may expose 90 minutes as well.

The Collective Sitting feature must reuse the existing timer rather than implementing a second independent meditation timer.

---

# 6. Recurring Commitment

The user creates a recurring sitting commitment.

Example:

```text
Every day
6:30 AM
30 minutes
```

Days should support:

- Every day
- Weekdays
- Weekends
- Custom days

Every day should be the default.

---

# 7. Schedule Changes

Changing the schedule should be a deliberate action.

Example:

```text
Current commitment

6:30–7:00 AM
Every day

Change schedule?
```

After selecting a new schedule:

```text
New commitment

7:00–7:30 AM
Every day

[Confirm change]
```

The system should not make changing the commitment feel equivalent to changing an ordinary app preference.

The intention is to reinforce commitment.

---

# 8. Collective Session

A collective session is created for users with compatible schedules.

V1 should use deterministic grouping:

```text
Local date
+
Timezone
+
Exact start time
+
Duration
```

Example:

```text
Date: 2026-09-06
Timezone: Asia/Kolkata
Start: 06:30
Duration: 30 minutes
```

Users with the same session parameters belong to the same Meditation Hall.

Do not implement fuzzy matching in V1.

---

# 9. Pre-Sit Experience

Approximately five minutes before the scheduled start, the user can enter the Meditation Hall.

Example:

```text
MEDITATION HALL

        [avatars]

      14 people are here

Your sit starts in

03:21

[Enter Hall]
```

The user is not counted as sitting until they explicitly check in.

---

# 10. Meditation Hall

The Meditation Hall is the central visual component of the feature.

It should communicate:

> **Other people are here and preparing to sit.**

It should not behave like a virtual world or social network.

## Design characteristics

- Minimal
- Calm
- Static
- Anonymous
- Low visual stimulation
- No scrolling feed
- No interaction required

Conceptually:

```text
              🧘

        🧘          🧘

    🧘       🧘       🧘

          🧘      🧘


       14 people present
```

The actual implementation should use custom meditation avatars rather than emoji.

---

# 11. Avatar System

Users are represented by anonymous avatars.

Avatars should:

- look human
- represent meditation/sitting
- have visual diversity
- remain anonymous
- be calm and understated
- be static or nearly static

Possible variation:

- body type
- hair
- clothing
- skin tone
- sitting posture

The avatar should communicate:

> “A person is here.”

It should not communicate:

> “Look at this person's profile.”

---

# 12. Identity

User identity should not be shown by default.

The Hall should primarily show avatars and aggregate presence.

Names may be considered as a future optional interaction, but are not required for V1.

No user profile should be accessible from the Hall in V1.

---

# 13. Photographs

Profile photographs are not part of V1.

Rationale:

Photographs introduce unnecessary social dynamics:

- appearance comparison
- profile maintenance
- social pressure
- distraction
- identity concerns

Anonymous avatars preserve human presence without creating a social-media environment.

---

# 14. Daily Meditation Snap

Daily meditation photographs are explicitly excluded from V1.

The product should communicate:

> **“People are sitting now.”**

rather than:

> “People posted photographs of themselves meditating.”

Live presence is the social signal.

---

# 15. Arrival / Presence

A user may enter the Hall before the session.

The Hall should show the number of people currently present.

Example:

```text
6:27 AM

17 people are preparing
```

As more users arrive, the participant count can update.

Avoid attention-grabbing animations.

---

# 16. Start Check-In

The user must explicitly confirm that they are sitting.

For a scheduled start time `T`:

```text
Valid check-in window:
T - 5 minutes
through
T + 5 minutes
```

Example:

```text
Scheduled:
6:30 AM

Valid check-in:
6:25–6:35 AM
```

Primary CTA:

> **I'm Sitting**

After confirmation:

> **You're in.**

The user's avatar becomes part of the sitting group.

---

# 17. Attendance State Machine

The attendance lifecycle is:

```text
Scheduled
    ↓
Entered Hall
    ↓
Checked In
    ↓
Sitting
    ↓
Completed
```

Possible exceptional states:

```text
Missed Check-in
Late Start
Incomplete
Cancelled
Abandoned
```

---

# 18. Start Discipline

The system records both:

- scheduled start
- actual check-in/start

Example:

```text
Scheduled: 6:30
Actual:    6:28
Status:    On-time
```

If the user checks in at 6:34:

```text
Scheduled: 6:30
Actual:    6:34
Status:    Late
```

Late users should still be allowed to meditate.

The system measures discipline; it does not punish practice.

---

# 19. Starting the Meditation

At the scheduled start, checked-in users enter the meditation session.

The existing Vipassana Timer must be reused.

Architecture:

```text
Collective Sitting
        ↓
Collective Session Controller
        ↓
Existing Vipassana Timer
```

The Collective Sitting feature should not implement a second timer engine.

---

# 20. During Meditation

Once meditation begins, the UI should become extremely minimal.

Possible information:

```text
              6:43 AM


                 avatar

           other avatars


          17 people sitting

              17:02
```

No:

- chat
- comments
- reactions
- social activity
- profile browsing
- achievements
- changing feeds
- unnecessary animations

The goal is for the user to stop interacting with the phone.

---

# 21. Participant Count

Display a simple aggregate:

> **17 people sitting with you**

The count can update during the session.

Do not show individual join/leave notifications.

Avoid:

> Rahul joined  
> Priya left  
> Amit completed

This would turn collective presence into social monitoring.

---

# 22. Empty Hall

The experience must work when nobody else is present.

Example:

```text
MEDITATION HALL

             🧘

       You are the first one here.
```

Never create fake participants.

Never imply that other people are present when they are not.

---

# 23. Large Sessions

The visual representation should scale without attempting to render hundreds of complex avatars.

For large sessions, the Hall can display a bounded collection of representative avatars plus an aggregate count.

Example:

```text
       [avatars]
     [avatars]
   [avatars]

       127 sitting
```

The count is more important than showing every individual.

---

# 24. Completion

At the scheduled end, the existing timer completes.

For scheduled end `T`:

```text
Valid completion window:
T - 5 minutes
through
T + 5 minutes
```

Example:

```text
Scheduled end:
7:00 AM

Valid completion:
6:55–7:05 AM
```

Primary CTA:

> **Complete Sit**

---

# 25. Completion Record

Example:

```text
Sit complete

30 minutes
6:30–7:00 AM

17 people sat with you.

[Done]
```

The wording should remain calm.

Avoid:

- Congratulations
- streak celebrations
- badges
- points
- motivational messages

---

# 26. Completion Discipline

Record:

- scheduled end
- actual completion
- whether completion was within the allowed window

Example:

```text
Scheduled end: 7:00
Actual end:    7:01
Status:        On-time
```

If the user completes at 6:58:

```text
Status: Early completion
```

The user is still allowed to complete the sit.

---

# 27. Practice vs Commitment Metrics

The system should distinguish:

### Practice consistency

> Did the user complete the scheduled meditation?

### Start discipline

> Did the user start/check in within the allowed window?

### Completion discipline

> Did the user complete within the allowed window?

Example:

```text
Last 30 days

Sits completed
27 / 30

Started on time
25 / 30

Completed on time
26 / 30
```

These metrics are more useful than a simple “meditated today” flag.

---

# 28. Avoid Streak-Based Gamification

Do not make streaks the primary measure.

Avoid:

```text
🔥 27 day streak
```

Prefer:

```text
27 of last 30 sits completed
```

The system should encourage returning to practice after a missed sit rather than making one missed day psychologically catastrophic.

---

# 29. Missed Sit

If the user does not check in:

```text
You missed today's sit.

Your next scheduled sit:
Tomorrow · 6:30 AM
```

No shame-oriented language.

No punishment.

No forced explanation.

---

# 30. Late Sit

If the user checks in outside the normal start window but still wishes to meditate:

```text
Late check-in

Scheduled:
6:30 AM

Checked in:
6:41 AM

[Begin Sit]
```

Record the session as late.

Do not prevent the user from meditating.

---

# 31. Early / Late Completion

Users may complete outside the preferred completion window.

The system records the actual behavior but does not block practice.

Example:

```text
Scheduled:
6:30–7:00

Actual:
6:30–6:58

Status:
Completed early
```

The accountability mechanism measures behavior rather than obstructing it.

---

# 32. Daily Home Screen

The existing Vipassana Timer home screen should expose Collective Sitting as a primary option.

Example:

```text
TODAY

6:30 AM
30 min

17 people sitting

[Join Sit]
```

If no collective schedule exists:

```text
Create your daily sitting commitment

[Choose a time]
```

---

# 33. Primary CTA States

Before session:

> **Join Sit**

Pre-sit:

> **Enter Hall**

During check-in:

> **I'm Sitting**

After scheduled end:

> **Complete Sit**

Keep the primary action obvious and singular.

---

# 34. Notifications

Minimal reminders should be supported.

Recommended:

### 15 minutes before

> Your 6:30 AM sit is coming up.

### 5 minutes before

> Your sit starts in 5 minutes.

### Start

> Your sit is starting.

### End

> Your sit is complete.

Notifications should be configurable.

No Collective Sitting notifications should interrupt the actual meditation.

---

# 35. Time Zones

Schedules are stored relative to the user's local timezone.

Example:

```text
Start:
06:30

Timezone:
Asia/Kolkata
```

The app must correctly handle daylight-saving/timezone transitions for users outside India.

If the user changes timezone, the product should have an explicit and predictable policy for whether the commitment follows local clock time.

Recommended default:

> **Keep the same local clock time.**

---

# 36. Connectivity

The meditation itself should remain resilient to network problems.

### Network-dependent

- Entering Hall
- Live participant count
- Live presence synchronization
- Uploading attendance

### Network-independent

- Meditation timer
- Actual meditation session
- Local recording of completion

If connectivity disappears during a sit:

> Continue meditating.

Attendance should synchronize when connectivity returns.

---

# 37. Privacy

V1 should expose minimal information.

Other participants can see only:

- anonymous avatar
- collective presence
- aggregate participant count

They cannot see:

- phone number
- email
- location
- meditation history
- attendance history
- personal statistics
- photograph

---

# 38. No Social Interaction

V1 deliberately excludes:

- Chat
- Comments
- Direct messages
- Likes
- Reactions
- Followers
- Following
- Profiles
- Social feeds

The Hall represents **co-presence**, not communication.

---

# 39. No Surveillance

The product should not attempt to verify whether someone is physically meditating.

Do not use:

- camera
- microphone
- movement detection
- biometric verification
- phone-use monitoring

The user makes the commitment.

The system records what the user confirms.

The goal is accountability, not policing.

# 41. Live Presence vs Historical Attendance

These must be modeled separately.

### Live presence

> “This user is currently in the Hall.”

Temporary state.

### Historical attendance

> “This user completed their 6:30–7:00 sit.”

Permanent practice record.

Do not use historical attendance as the source of truth for live Hall presence.

The feature should sit on top of the existing Vipassana Timer.

```text
                  Vipassana Timer
                         │
              ┌──────────┴──────────┐
              │                     │
         Local Timer          Collective Sitting
                                    │
                           ┌────────┴────────┐
                           │                 │
                       Schedule        Live Presence
                           │                 │
                           └────────┬────────┘
                                    │
                              Session Backend
                                    │
                           ┌────────┴────────┐
                           │                 │
                       Attendance        Hall State
```

The existing timer remains independently functional.

---

# 48. Existing Timer Integration

Collective Sitting must invoke the existing meditation timer.

Required integration points:

```text
startSession(duration)
pause/resume behavior if supported
endSession()
session completion callback
local persistence
```

The Collective Sitting module should not duplicate timer logic.

---

# 49. Synchronization

The collective session needs a server-authoritative scheduled start/end timestamp.

Clients should not independently decide when the collective session begins.

Use server time where possible to prevent device-clock discrepancies.

The actual timer can remain locally resilient while the collective session uses synchronized timestamps.

---

# 50. Participant Matching

V1 matching key:

```text
local_date
timezone
exact_start_time
duration
```

Example:

```text
2026-09-06
Asia/Kolkata
06:30
30
```

All compatible participants enter the same session.

No fuzzy time matching in V1.

---

# 51. Hall Behavior When Nobody Else Is Present

Do not create artificial social proof.

If the user is alone:

> **You're the first one here.**

This can eventually become a positive signal without compromising trust.

---

# 52. Product Success Metrics

The primary metric is not DAU.

## Primary

### Scheduled Sit Completion Rate

```text
completed scheduled sits
------------------------
scheduled sits
```

## Secondary

### On-Time Start Rate

```text
on-time starts
--------------
scheduled sits
```

### On-Time Completion Rate

```text
on-time completions
-------------------
scheduled sits
```

### 30-Day Continuity

Percentage of users completing a meaningful percentage of scheduled sits over 30 days.

## Collective metric

### Collective Participation

Number of sessions in which two or more real participants actually sat together.

This validates the central premise of the feature.

---

# 53. Core Product Experiment

The most important hypothesis is:

> **Seeing other people sitting at the same time increases the probability that a meditator shows up and completes their scheduled sit.**

Potential future experiment:

### Control

Existing Vipassana Timer only.

### Variant A

Timer + scheduled Collective Sitting.

### Variant B

Timer + Collective Sitting + live participant presence.

Compare:

- scheduled-sit completion
- on-time starts
- 30-day continuity

The objective is to establish whether collective presence materially improves discipline.

---

# 54. Design Rules

Every design decision should satisfy these rules:

1. **Practice over engagement**
2. **Presence over social interaction**
3. **Commitment over motivation**
4. **Anonymous presence over identity**
5. **Live presence over photographs**
6. **Measurement over gamification**
7. **Recovery over punishment**
8. **Minimal UI during meditation**
9. **No surveillance**
10. **The app should disappear once meditation begins**

# 56. V1 Definition of Done

The feature is ready for release when a user can:

- create a recurring daily sitting commitment
- choose an exact start time
- choose duration
- receive a reminder
- enter the Meditation Hall
- see real participants represented by anonymous avatars
- see the current participant count
- check in within the allowed window
- start the existing Vipassana Timer
- meditate without requiring network connectivity throughout the entire session
- complete the sit
- confirm completion
- have attendance synchronized to the backend
- see the session in personal history
- see basic continuity statistics
- miss a session without being blocked from the next session
- change their future schedule

The system must:

- never fabricate participants
- never expose unnecessary personal information
- never require camera/microphone surveillance
- never turn the Hall into a social feed
- never prevent someone from meditating because they missed an accountability window
- preserve the integrity of the existing Vipassana Timer

# 57. Future Feature Boundary

The next feature — **Buddy Support** — should build on the data generated here.

This feature should establish:

```text
Who committed?
Who showed up?
Who started on time?
Who completed?
Who maintains continuity?
Who appears to be struggling?
```

Only after this foundation exists should the product introduce:

```text
Struggling practitioner
        ↓
Request help
        ↓
Match with reliable practitioner
        ↓
7-day buddy sitting
        ↓
Measure whether continuity improves
```

That is deliberately outside the scope of Feature 1.
